#coding-standards.md
## 개요

이 규칙은 AIDD 팀의 모든 프로젝트에 적용되는 기본 코딩 원칙을 정의합니다.
객체지향적 설계 원칙을 기반으로 하며, 확장 가능하고 유지보수하기 쉬운 코드 작성을 목표로 합니다.


## 기본 원칙
### 1. 단일 책임 원칙 (SRP)
- 각 클래스/함수는 하나의 명확한 책임만 가져야 함
- 변경 이유가 하나여야 함
### 2. 개방-폐쇄 원칙 (OCP)
- 확장에는 열려있고, 수정에는 닫혀있어야 함
- 인터페이스와 추상화를 활용
### 3. 리스코프 치환 원칙 (LSP)
- 하위 타입은 상위 타입을 대체할 수 있어야 함
- 계약을 준수해야 함
### 4. 인터페이스 분리 원칙 (ISP)
- 클라이언트는 사용하지 않는 인터페이스에 의존하지 않아야 함
- 작고 구체적인 인터페이스 사용
### 5. 의존성 역전 원칙 (DIP)
- 고수준 모듈은 저수준 모듈에 의존하지 않아야 함
- 추상화에 의존해야 함


## 코드 품질 기준
### 가독성
- 명확하고 의미있는 이름 사용
- 적절한 들여쓰기와 포맷팅
- 주석은 왜(Why)에 집중
- import를 활용하고 불필요한 fullpath type 사용 금지
- class의 field 선언은 항상 최상단에 존재
### 테스트 가능성
- 단위 테스트 가능한 구조
- 의존성 주입 활용
- Mock 가능한 인터페이스 설계
### 성능
- 불필요한 객체 생성 방지
- 적절한 알고리즘 선택
- 메모리 누수 방지


## 네이밍 컨벤션
### 클래스/인터페이스
- 명사형, PascalCase
- 역할을 명확히 표현
- 예: `UserService`, `PaymentProcessor`
### 메서드/함수
- 동사형, camelCase
- 동작을 명확히 표현
- 예: `processPayment()`, `validateUser()`
### 변수/상수
- 의미있는 이름, camelCase
- 약어 사용 지양
- 예: `userCount`, `MAX_RETRY_COUNT`


## 에러 처리
### 예외 처리 원칙
- 예외는 예외적인 상황에만 사용
- 구체적인 예외 타입 사용
- 적절한 로깅과 모니터링
### 방어적 프로그래밍
- 입력값 검증
- null 체크
- 경계 조건 처리

- [ ] 보안 취약점이 없는가?
